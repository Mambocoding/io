## 0.2.263

owes: none — the Netty pin returns to 4.2.17.Final, the version Ktor 3.6.0 brings, so every io.netty module resolves to one version again; no migration, no configuration key.
owes: take a snapshot right after updating: every snapshot now carries a signature (`integrity.mac`) made with a new key file, `integrity.key`, which the hub creates beside `secret.key` at its first start; an earlier snapshot is not signed, so it restores only onto a new hub that was never paired, and a hub in use refuses to upload or restore it (SPEC-183 §2, §3).
owes: back up `/data/integrity.key` with the rest of `/data`: it is never in a snapshot and never downloadable, and a snapshot made by a hub that lost it restores only onto a new, never-paired hub (SPEC-183 §1).
owes: recovery codes are re-keyed at the first start: each stored value becomes a keyed hash under `integrity.key` (`k0:` for a code made before, `k1:` for a new one), and a printed code keeps working; a rollback to an earlier release makes every recovery code unusable until each account regenerates them (second-factor codes from the app keep working). An account whose codes predate the update is asked on *Settings, Account* to make new ones, because a snapshot copied before the update still holds them as plain SHA-256. A hub that loses `integrity.key` removes its keyed codes at the next start and logs how many (SPEC-183 §7). No migration.
owes: a restore on a hub in use no longer rolls back a credential change: an account in both the hub and the snapshot keeps its current password, role, second factor, devices and file tokens, and only accounts the snapshot has and the hub lacks come back with theirs; the restore page lists them. A bad password reset is answered with the existing password and second-factor reset routes, not a restore (SPEC-183 §4).
owes: a restore keeps this machine's `BIND`, `PORT` and `ALLOWED_HOSTS` and any setting the environment's rules would refuse (SPEC-183 §6); and `SYNCHUB_FILE_AREA_UPLOAD_MAX_BYTES` and `SYNCHUB_BLOB_UPLOAD_MAX_BYTES` above 2048 MiB now refuse start, as the setup page has always capped them (a changed default). No migration.
owes: a migration — schema V036 (`devices.endorsed_by`, `pairing_codes.endorsed_by`, REV-HUBSEC-02), forward-only: an older image refuses a database at 36, so a rollback after the first start needs a snapshot taken before it. A device paired through another device's `POST /devices/pair/delegate` is now deleted with its endorser (revoking a stolen phone revokes every device it endorsed, those they endorsed, and its unredeemed codes), Settings → Devices says *paired through …*, and one device may endorse ten pairings an hour (the eleventh answers `429 {"error":"rate_limited"}`); a device paired before this release has no endorser, so revoking it takes nothing else. No configuration key.
owes: a changed default — sign-in attempts on one account are answered one after another, each after its own delay, so N parallel wrong guesses at one account take the sum of their delays instead of the longest (REV-HUBSEC-10); an uploaded snapshot (page, wizard or API) is kept as its own kind, never pruned, never counted toward the three daily and two monthly, and deleted like a manual one (REV-HUBSEC-14), where an uploaded file labelled `daily` could push a real one out; a restore refuses a snapshot of more than 200 000 entries or one that inflates past the larger of 64 MiB and fifty times its own size (`snapshot-too-many-entries`, `snapshot-too-large`, REV-HUBSEC-11). No migration, no configuration key, rollback safe.
