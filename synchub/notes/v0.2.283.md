owes: SyncDesk — `uiModel` 26 (SPEC-199 §2-§4): `AccuracyCardFact` drops `lastReadingAgoMillis` for `lastFoldedAgoMillis` (the last reading the hub kept, not the last message), and gains `unreadableCount` and `collectingDays`, one `AccuracyDayFact` (`date`, `covered`, `needed`, `longestSilenceHours`, `forecast`, `counted`, `noReading`) per local day before today; the engine's strings gain `weather.accuracy.collectingUnreadable`, `collectingSomeUnreadable`, `dayCounted`, `dayNoForecast`, `dayNoReading` and `dayNotCounted` in five locales. SyncDesk raises its floor to 26 and draws the facts the hub's body draws. No migration, no configuration key, no wire change.
owes: a changed behaviour (SPEC-199 §1) — a weather sensor's folded hours are written every five minutes instead of hourly, and a clean stop (a restart, the module toggle) now waits up to five seconds for the final write before the database closes, so a restart no longer loses the readings of the hour. The write is the existing merge upsert; no migration, no configuration key. A hard kill loses at most five minutes.
owes: a changed behaviour (SPEC-198 §1, REV-HUB-30) — the tennis season request has its own 120 s deadline (was the 30 s every dial shares) and the hub holds the season body once instead of several times over, so a hub in a 512 MB container no longer risks running out of memory on the daily calendar. No configuration key, no migration.
owes: a migration (SPEC-025 *Claims per use*, SPEC-173 §3, REV-HUBSEC-22) — schema V041, forward-only: `blob_claims` is rebuilt with a `use` (`device`, or `backup:<app>`) in its primary key. A digest a backup entry names becomes a `backup:<app>` row per app naming it, every other claim a `device` row; no file is touched. A rollback after the first start needs a backup of the database taken before it, and an older image cannot read the table. A backup-scoped token now registers (`POST /backups/<app>`, else `409 blob_missing`) and probes (`HEAD`, else `404`) only a digest its own app's upload holds; a full token's `DELETE` drops only its `device` claim, so a file a backup entry names stays, and removing or pruning an entry releases only that app's claim.
owes: SyncDesk — the engine closes a connection that sends no `hello` within 5 s (SPEC-134 §3, REV-HUBSEC-23), so a silent peer no longer holds its only connection; SyncDesk already sends `hello` first and at once, so nothing changes for it, but any other client of the engine socket must too. No migration, no configuration key, `uiModel` and the contract unchanged.
owes: a changed behaviour (SPEC-089 §4, D42, REV-HUBSEC-16) — sign-in attempts on one account no longer queue behind each other: one is checked at a time, and an attempt that arrives while another is being checked, or sooner than the delay the account's wrong attempts earned (1 s doubling to 60 s), is answered `429` at once with nothing checked and nothing recorded, where it used to wait its turn. This covers `/login`, `POST /api/v1/session`, the password and second-factor steps of the account page, and the other password-and-code step-ups; the sign-in page and the account pages say so in one sentence (five locales). A client that sends a right password just after a wrong one must retry after a moment (SyncDesk and the apps already treat `429` as "try again later"). No migration, no configuration key.
owes: a changed behaviour (SPEC-185 §4.1, D45, REV-HUBSEC-19) — on an IPv6 bind, a peer inside the hub's own on-link prefixes is now counted by its full address, not its `/64`, by the sign-in lock (5 failures) and the connection cap (32 sockets): one household device's wrong passwords or open sockets no longer shut out every other device on the LAN. An off-link IPv6 peer keeps the `/64`; IPv4 binds are unchanged. A lock already recorded under a `/64` key simply ages out of its window. No migration, no configuration key.
owes: a changed behaviour (SPEC-038, REV-HUB-32) — `DELETE` on the file area's root (`/files` or `/files/`) answers `403` and removes nothing, where it used to delete the whole area and recreate it empty. A file manager that empties the area deletes its entries one by one, which still works; a folder below the root deletes as before. No migration, no configuration key.
owes: SyncDesk, and any client of `/api/v1/users` (SPEC-184 §1.4, REV-HUBSEC-17) — creating an account that names any role asks for the calling admin's step-up. `POST /api/v1/users` and the engine's `admin.users.create` now take `{name, newPassword, roles?, password?, code?}`: **the new account's password moves from `password` to `newPassword`** (a request with only `password` and no `newPassword` is `400`), and `password`/`code` are the caller's step-up, required when `roles` is not empty (`400` missing, `401 invalid_credentials` or `second_factor_required`, `429`) and ignored otherwise. The new-account screen (`settings.userNew`) carries *Current password* (and *Current code* for an enrolled admin) inside its Roles group and its facts carry `user.callerHasSecondFactor`; `users.create` takes the fields `newPassword`, `password`, `code`. SyncDesk sends the renamed field and the step-up from that screen, as it does for the four other account actions. The web form `POST /admin/users` takes `newPassword` too. No `uiModel` change, no migration, no configuration key.
